# Vibe Coding Template 사용 가이드

## 1. 이 템플릿은 무엇인가?

이 템플릿은 ChatGPT, Claude Code, Codex 같은 AI 코딩 도구를 이용해 **작은~중간 규모의 개인 프로그램을 처음부터 구현하고 이후 수정까지 관리하기 위한 작업 방식**이다.

단순히 AI에게

> "이런 프로그램 만들어줘."

라고 요청하는 대신,

1. 무엇을 만들지 정리하고
2. 꼭 필요한 질문만 AI에게 받고
3. 설계·할 일 목록을 만든 뒤
4. AI에게 전체 MVP 구현을 맡기고
5. 이후 수정 사항은 별도의 Change Request로 관리한다.

이 방식의 목적은 문서를 많이 만드는 것이 아니다.

핵심은 다음 세 가지다.

- AI가 같은 질문을 반복하지 않게 한다.
- AI가 프로젝트의 현재 상태와 결정사항을 잊지 않게 한다.
- 사용자가 계속 중간 승인을 해주지 않아도 AI가 구현과 테스트를 끝까지 진행하게 한다.

---

# 2. 어떤 프로젝트에 적합한가?

주로 다음 정도의 개인 프로젝트를 대상으로 한다.

- Python 프로그램
- Qt GUI 프로그램
- PC용 유틸리티
- Android 앱
- 간단한 알고리즘 프로그램
- 개인 자동화 프로그램
- 약 10,000줄 이하의 소규모 프로젝트

대규모 팀 프로젝트나 수십만 줄 규모의 서비스라면 더 체계적인 요구사항 관리, 이슈 관리, CI/CD, 코드 리뷰 체계가 필요할 수 있다.

# 3. 전체 작업 흐름

처음에는 아래 순서만 기억하면 된다.

```text
① 만들 프로그램 정의
        ↓
01_프로그램기능.md

② 빠진 중요한 결정 확인
        ↓
10_보완질문요청.md
필요하면 11_보완질문요청.md

③ 결정사항 기록
        ↓
02_결정사항들.md

④ AI용 프로젝트 문서 생성
        ↓
20_기초문서작성요청.md

생성되는 파일:
AGENTS.md
docs/DESIGN.md
docs/DECISIONS.md
docs/TODO.md

⑤ MVP 전체 구현
        ↓
30_구현요청.md

⑥ 이후 기능 추가/버그 수정
        ↓
ChangeRequest.md를 복사해서 사용
```

즉, 처음 프로젝트를 만들 때는 크게

**요구사항 → 질문 → 기초 문서 → 구현**

순서로 진행한다.

한번 프로그램이 만들어진 이후에는 대부분

**Change Request → 수정 → 테스트**

만 반복하면 된다.

# 4. 각 파일은 무엇을 위한 것인가?

## `00_작업절차.md`

이 템플릿 전체의 사용 설명서이자 기본 원칙이다.

평소 AI에게 매번 전달할 파일은 아니다.

사용자가 템플릿의 작업 방식을 확인할 때 참고하면 된다.

---

## `01_프로그램기능.md`

### "무엇을 만들 것인가?"

를 기록하는 가장 중요한 사용자 문서다.

여기에는 다음 내용을 작성한다.

- 프로그램의 목표
- 실행 환경
- MVP 기능
- 각 기능의 완료 조건
- 오류가 났을 때의 동작
- 이번 버전에서 만들지 않을 기능

중요한 점은 **구현 방법을 여기 적지 않는 것**이다.

예를 들어 좋은 요구사항은 다음과 같다.

```text
기능:
텍스트 파일을 선택해서 내용을 화면에 표시한다.

완료 조건:
UTF-8 txt 파일을 선택하면 내용이 편집창에 표시된다.
```

반대로 다음과 같은 내용은 가능하면 적지 않는다.

```text
QFileDialog를 사용한다.
Model-View 구조를 사용한다.
TextLoader 클래스를 만든다.
```

이것들은 사용자 요구사항이 아니라 구현 방법이기 때문이다.

AI가 더 적절한 방법을 선택할 수 있도록 요구사항과 구현 방법을 분리한다.

---

# 5. `01_프로그램기능.md` 작성 방법

처음에는 완벽하게 작성할 필요가 없다.

템플릿의 빈칸을 아는 만큼만 채운다.

예를 들어 간단한 이미지 OCR 프로그램이라면 다음과 같이 작성할 수 있다.

```text
# 프로그램 기능

## 목표

사진을 열어 이미지 안의 글자를 OCR로 인식하고
사용자가 필요한 텍스트를 복사할 수 있는 프로그램을 만든다.

## 실행 환경

- 대상 플랫폼: Windows 11
- 언어: Python
- GUI: Qt
- 입력 데이터: JPG, PNG

## MVP 기능과 완료 조건

1. 이미지 열기
   - 완료 조건: JPG와 PNG 파일을 화면에 표시할 수 있다.

2. OCR 실행
   - 완료 조건: 이미지의 텍스트를 인식해 화면에 표시한다.

3. OCR 결과 복사
   - 완료 조건: 선택한 텍스트를 클립보드에 복사할 수 있다.

## 오류 시 동작

- 지원하지 않는 파일은 오류 메시지를 표시한다.
- OCR 실패 시 프로그램이 종료되지 않고 오류를 표시한다.

## 제외 범위

- PDF OCR
- 클라우드 동기화
- 사용자 계정
```

모르는 내용은 억지로 정할 필요 없다.

```text
[미정]
```

으로 남겨두면 된다.

그 부분은 다음 단계에서 AI에게 질문을 받는다.

# 6. `10_보완질문요청.md` 사용하기

`01_프로그램기능.md`를 작성했다면 이제 AI에게 **구현 전에 반드시 결정해야 하는 것이 빠졌는지 검사**하도록 한다.

AI 코딩 도구에게 다음 두 파일을 제공한다.

```text
01_프로그램기능.md
10_보완질문요청.md
```

그리고 `10_보완질문요청.md`의 내용을 그대로 실행하도록 요청한다.

이 파일은 AI에게 다음과 같이 지시한다.

> 구현을 막는 중요한 미결 사항만 질문해라.

질문 개수도 최대 10개로 제한한다.

따라서 AI가 다음과 같은 사소한 질문을 끝없이 하는 것을 막는다.

```text
버튼 색깔은 무엇으로 할까요?
클래스 이름은 어떻게 할까요?
폴더 이름은 무엇으로 할까요?
```

이런 것은 AI가 합리적인 기본값을 선택하도록 한다.

---

# 7. AI가 질문하면 어떻게 해야 하나?

AI가 질문을 하면 답을 정하고 그 결과를

`02_결정사항들.md`

에 작성한다.

예:

```text
| ID | 결정 | 이유 또는 영향 |
|---|---|---|
| D-001 | OCR은 로컬에서 실행한다. | 인터넷 없이 사용할 수 있어야 함 |
| D-002 | 입력은 JPG와 PNG만 지원한다. | MVP 범위 제한 |
| D-003 | OCR 실패 시 오류 메시지를 표시한다. | 프로그램 강제 종료 방지 |
```

확실하게 정하지 못했지만 개발을 위해 임시로 선택하는 것도 기록할 수 있다.

예:

```text
| ID | 가정 | 확인이 필요한 시점 |
|---|---|---|
| A-001 | 기본 OCR 언어를 한국어+영어로 한다. | 실제 OCR 정확도 테스트 후 |
```

# 8. `11_보완질문요청.md`는 언제 사용하는가?

대부분 프로젝트에서는 사용하지 않아도 된다.

다음 경우에만 사용한다.

- 1차 질문에 답했는데도 중요한 미결 사항이 남은 경우
- 요구사항을 크게 변경한 경우
- 보안이나 데이터 손실처럼 잘못 결정하면 위험한 내용이 있는 경우

이때 AI에게

```text
01_프로그램기능.md
02_결정사항들.md
11_보완질문요청.md
```

를 전달한다.

AI는 이미 질문했던 내용을 반복하지 않고 **새롭게 결정해야 할 중요한 내용만 최대 5개** 찾아야 한다.

추가 문제가 없다면 이 단계는 바로 끝낸다.

---

# 9. 이제 기초 문서를 만든다

요구사항과 중요한 결정이 정해졌다면

`20_기초문서작성요청.md`

를 사용한다.

AI에게 최소한 다음 파일을 제공한다.

```text
01_프로그램기능.md
02_결정사항들.md
20_기초문서작성요청.md
```

이미 코드가 있는 프로젝트라면 AI가 현재 저장소도 함께 확인하도록 한다.

이 요청을 실행하면 AI는 다음 네 파일을 만든다.

```text
AGENTS.md

docs/
├── DESIGN.md
├── DECISIONS.md
└── TODO.md
```

이 네 파일은 앞으로 AI가 프로젝트를 이해하기 위한 핵심 정보가 된다.

---

# 10. `AGENTS.md`란?

쉽게 말하면

> **이 프로젝트에서 AI 개발자가 항상 지켜야 하는 작업 규칙**

이다.

예를 들어 다음 내용이 들어갈 수 있다.

```text
- Python 3.12 사용
- pytest로 테스트
- 기존 사용자 변경을 임의로 되돌리지 않음
- MVP 구현 시 중간 승인을 반복해서 요구하지 않음
- 사소한 구현 선택은 AI가 판단
```

중요한 점은 모든 개발 상식을 적는 것이 아니다.

예를 들어 이런 것은 굳이 적을 필요가 없다.

```text
좋은 코드를 작성한다.
버그가 없도록 한다.
변수명을 잘 작성한다.
```

AI가 이미 알고 있는 일반적인 원칙이기 때문이다.

**이 프로젝트에만 필요한 규칙**을 기록한다.

---

# 11. `docs/DESIGN.md`란?

프로그램의 **현재 구조**를 기록한다.

예:

```text
UI
 ↓
OCRService
 ↓
OCR Engine

ImageView
 ↓
CoordinateConverter
 ↓
OCR Bounding Box
```

주로 다음 내용이 들어간다.

- 프로그램 주요 구성 요소
- 데이터 흐름
- 상태 관리 방법
- 주요 인터페이스
- 오류 처리 방식

DESIGN은 미래의 희망사항을 적는 문서가 아니다.

현재 실제 구조를 기준으로 작성한다.

아직 구현되지 않은 내용이라면

```text
계획
가정
```

등으로 명확하게 표시한다.

---

# 12. `docs/DECISIONS.md`란?

프로젝트를 만들면서 내려진 **중요한 결정과 그 이유**를 기록한다.

예:

```text
D-004

결정:
SQLite를 사용한다.

이유:
별도 DB 서버 없이 로컬에서 사용할 수 있어야 한다.

영향:
데이터 저장 계층은 SQLite를 기준으로 구현한다.
```

왜 이런 문서가 필요한가?

몇 주 뒤 AI에게 수정 작업을 요청했는데 AI가

> SQLite 대신 JSON으로 바꾸는 것이 더 간단합니다.

라고 제안할 수도 있다.

DECISIONS에 기존 결정이 남아 있으면 AI는 이전 결정의 이유를 확인할 수 있다.

---

# 13. `02_결정사항들.md`와 `DECISIONS.md`의 차이

처음 보면 가장 헷갈리기 쉬운 부분이다.

### `02_결정사항들.md`

프로젝트 시작 전에 사용자와 AI가 질문·답변하면서 만든 **초기 인터뷰 기록**

### `docs/DECISIONS.md`

실제 개발이 시작된 이후 관리하는 **현재 프로젝트의 공식 결정사항**

이다.

기초 문서를 만든 이후부터는 중요한 결정은

```text
docs/DECISIONS.md
```

에서 관리한다.

두 문서를 계속 똑같이 업데이트할 필요가 없다.

---

# 14. `docs/TODO.md`란?

AI가 MVP를 완성하기 위해 해야 할 일을 기록한다.

단순 메모 목록이 아니라 **구현 체크리스트**라고 생각하면 된다.

예:

```text
필수 구현

[ ] 이미지 로딩
    완료 조건:
    JPG/PNG 파일을 열 수 있음

[ ] OCR 실행
    완료 조건:
    이미지에서 텍스트 추출 가능

[ ] 결과 복사
    완료 조건:
    선택한 문자열을 클립보드에 복사 가능

통합 검증

[ ] 이미지 열기 → OCR → 복사 전체 흐름 테스트
```

TODO는 가능한 한 실제 개발 순서에 맞게 작성한다.

그러나

```text
Step 1 끝나면 사용자에게 확인
Step 2 끝나면 다시 요청
```

처럼 사용할 필요는 없다.

AI가 내부적으로 순서대로 처리하지만 **사용자는 MVP 구현을 한 번만 요청**한다.

---

# 15. 실제 MVP 구현하기

기초 문서가 완성되었다면

`30_구현요청.md`

를 AI에게 실행시킨다.

AI는 다음 문서를 참고한다.

```text
AGENTS.md
docs/DESIGN.md
docs/DECISIONS.md
docs/TODO.md
```

그리고 현재 코드 상태를 확인하여 MVP 전체를 구현한다.

중요한 점은 여기서 말하는

> "한 번에 구현"

의 의미다.

AI가 모든 코드를 무작정 한 번에 작성한다는 뜻이 아니다.

예를 들어 내부적으로는 다음처럼 진행할 수 있다.

```text
파일 로딩 구현
→ 테스트

OCR 구현
→ 테스트

UI 연결
→ 테스트

전체 통합
→ 전체 테스트
```

하지만 매 단계마다

> 파일 로딩이 끝났습니다. 다음으로 진행할까요?

라고 사용자에게 묻지 않는다.

**한 번의 사용자 요청 안에서 필요한 구현과 검증을 계속 진행한다.**

---

# 16. AI가 구현할 때 해야 하는 일

`30_구현요청.md`는 AI에게 다음 작업까지 요구한다.

1. 현재 코드와 변경 상태 확인
2. 기존 사용자 코드 보존
3. MVP 전체 구현
4. 테스트·빌드·정적 검사
5. 실패 원인 수정
6. 테스트 재실행
7. 완료 조건 확인
8. 필요할 때만 DESIGN/DECISIONS 수정
9. TODO 정리
10. 결과 보고

따라서 단순히

> 코드를 작성했습니다.

에서 작업이 끝나는 것이 아니다.

**실제로 실행하거나 검증한 결과**를 기준으로 완료 여부를 판단한다.

---

# 17. 구현 결과는 무엇을 확인하면 되는가?

AI의 긴 설명을 읽을 필요는 없다.

최소한 다음 네 가지만 확인하면 된다.

### 전체 구현 여부

MVP가 전부 구현되었는가?

### 변경 내용

어떤 기능을 만들었는가?

### 검증 결과

테스트 또는 빌드가 성공했는가?

### 남은 문제

직접 기기에서 확인해야 하는 것 등 미완료 항목이 있는가?

템플릿 자체도 AI가 이 정도만 간결하게 보고하도록 요구한다.

---

# 18. 프로그램 완성 후 수정하려면?

초기 MVP가 만들어지고 나면

`01_프로그램기능.md`부터 다시 시작할 필요가 없다.

버그 수정이나 기능 추가는 `ChangeRequest.md`를 사용한다.

원본 파일은 그대로 보관하고 복사한다.

예:

```text
docs/tasks/
├── ChangeRequest.md
├── 001_ocr위치오류.md
├── 002_파일저장추가.md
└── 003_회전오류.md
```

번호를 붙이면 나중에 어떤 작업이었는지 찾기 쉽다.

---

# 19. Change Request 작성 방법

예를 들어 OCR 선택 영역이 어긋나는 버그가 있다고 하자.

다음처럼 작성한다.

```text
# Task-001

OCR 선택 영역이 실제 글자 위치와 어긋나는 문제 수정

## Current Problem

Portrait 사진에서 화면 아래쪽으로 갈수록
OCR bounding box가 실제 글자와 어긋난다.

## Expected

1. OCR 영역이 실제 글자와 일치한다.
2. 화면 회전 후에도 정상 동작한다.
3. 기존 OCR 기능은 유지된다.
```

여기서 가장 중요한 것은

### Current Problem

현재 무엇이 잘못되었는지

### Expected

수정 후 무엇이 되어야 하는지

두 가지다.

---

# 20. `Done When`이 중요한 이유

Change Request에는 완료 조건이 있다.

예:

```text
- 요구 기능 동작
- 기존 기능 regression 없음
- 관련 테스트 통과
- Debug build 성공
- 임시 코드 없음
- 문서와 실제 구현 일치
```

이것이 중요한 이유는 AI가

> 코드를 수정했으니 완료했습니다.

라고 판단하는 것을 막기 때문이다.

코드를 작성한 것과 문제를 해결한 것은 다르다.

이 템플릿에서는 가능하면

**코드 작성 → 테스트 → 완료 조건 확인**

까지 해야 완료다.

---

# 21. 수정 후 문서는 전부 다시 작성해야 하나?

아니다.

실제 변경이 있을 때만 수정한다.

### 코드만 조금 수정

```text
DESIGN 변경 X
DECISIONS 변경 X
TODO 변경 X
```

### 프로그램 구조 변경

```text
DESIGN 업데이트
```

### 새로운 중요한 기술 결정

```text
DECISIONS 업데이트
```

### 아직 해야 할 일이 생김

```text
TODO 업데이트
```

문서를 유지하기 위해 문서를 수정하는 것이 아니다.

**실제 프로젝트 상태가 달라졌을 때만 문서를 수정한다.**

---

# 22. 가장 기본적인 실제 사용 예

처음 프로그램을 만든다고 하자.

## Step 1

`01_프로그램기능.md`를 작성한다.

---

## Step 2

AI에게 다음을 전달한다.

```text
01_프로그램기능.md
10_보완질문요청.md
```

그리고 질문에 답한다.

---

## Step 3

답변 결과를

```text
02_결정사항들.md
```

에 기록한다.

---

## Step 4

필요한 경우에만

```text
11_보완질문요청.md
```

으로 한 번 더 확인한다.

일반적인 프로젝트라면 생략할 수 있다.

---

## Step 5

AI에게

```text
01_프로그램기능.md
02_결정사항들.md
20_기초문서작성요청.md
```

를 전달한다.

AI가 다음 파일을 만든다.

```text
AGENTS.md
docs/DESIGN.md
docs/DECISIONS.md
docs/TODO.md
```

---

## Step 6

`30_구현요청.md`를 실행한다.

AI가 MVP 전체 구현과 테스트를 진행한다.

---

## Step 7

프로그램을 직접 사용해 본다.

문제가 없다면 MVP 완료다.

---

## Step 8

나중에 버그가 발견되면

```text
ChangeRequest.md
```

를 복사한다.

예:

```text
001_ocr좌표오류.md
```

문제를 적고 AI에게 수정하도록 한다.

---

# 23. 기존 프로젝트에 적용하는 경우

반드시 새 프로젝트에서만 사용할 필요는 없다.

이미 코드가 있다면 다음처럼 시작해도 된다.

먼저 현재 프로그램이 무엇을 하는지 기준으로 `01_프로그램기능.md`를 작성한다.

그다음

```text
20_기초문서작성요청.md
```

을 실행한다.

AI가 기존 코드를 읽어 현재 상태를 기준으로

```text
AGENTS.md
DESIGN.md
DECISIONS.md
TODO.md
```

를 만들게 한다.

이후부터 동일한 방식으로 관리하면 된다.

# 24. 자주 하는 실수

## 요구사항 문서에 설계를 너무 많이 적기

잘못된 예:

```text
Controller 클래스를 만들고 Singleton으로 구현하고
JSONManager를 통해 저장한다.
```

특별한 이유가 없다면 AI에게 구현 방법을 맡긴다.

---

## 모든 것을 처음부터 결정하려고 하기

작은 개인 프로젝트에서는 변경하기 쉬운 선택까지 미리 결정할 필요가 없다.

예:

- 변수 이름
- 클래스 파일 이름
- 버튼 내부 구현
- 작은 라이브러리 사용 방식

등은 AI가 판단하게 둔다.

---

## 질문을 너무 많이 받기

AI가 구현에 필요하지 않은 질문까지 하기 시작하면 이 템플릿의 목적과 맞지 않는다.

`10_보완질문요청.md`는

> MVP 구현을 막는 질문만

하도록 만들어져 있다.

---

## TODO를 개발 일지로 만들기

다음처럼 완료 기록이 계속 쌓이면 안 된다.

```text
[x] 버튼 생성
[x] 버튼 위치 변경
[x] 버튼 색 변경
[x] 이벤트 연결
[x] 이벤트 수정
...
```

TODO는 **현재 무엇이 남았는지**를 파악하기 위한 문서다.

오래된 완료 이력은 필요하지 않다면 제거한다.

---

## AI 설명만 믿고 완료 처리하기

가장 중요한 원칙이다.

AI가

> 정상적으로 동작할 것입니다.

라고 말하는 것과 실제로 정상 동작하는 것은 다르다.

가능하면 다음을 확인한다.

```text
테스트 PASS
빌드 성공
실제 실행 성공
완료 조건 만족
```

---

# 25. 문서가 많아 보이는데 전부 매번 사용해야 하나?

아니다.

프로젝트 시작 단계에서만 여러 파일이 필요하다.

### 처음 프로젝트를 만드는 동안

```text
01_프로그램기능
02_결정사항
AGENTS
DESIGN
DECISIONS
TODO
```

가 만들어진다.

### 개발이 안정된 이후

사용자가 직접 작성하는 것은 대부분

```text
Change Request
```

뿐이다.

나머지 프로젝트 문서는 AI가 필요할 때 확인하고 실제 상태가 바뀔 때만 갱신한다.

---

# 26. 각 문서를 한 문장으로 기억하기

| 파일 | 한 문장으로 이해하기 |
|---|---|
| `01_프로그램기능.md` | **무엇을 만들 것인가?** |
| `02_결정사항들.md` | **시작 전에 무엇을 결정했는가?** |
| `AGENTS.md` | **AI가 이 프로젝트에서 어떻게 일해야 하는가?** |
| `DESIGN.md` | **현재 프로그램은 어떻게 구성되어 있는가?** |
| `DECISIONS.md` | **왜 이렇게 만들기로 했는가?** |
| `TODO.md` | **지금 무엇이 남았는가?** |
| `ChangeRequest.md` | **이번에 무엇을 고쳐야 하는가?** |

이 일곱 문장만 이해하면 템플릿의 대부분을 이해한 것이다.

---

# 27. 전체 사용법 초간단 요약

## 처음 만들 때

```text
01_프로그램기능 작성
        ↓
10_보완질문 실행
        ↓
02_결정사항 작성
        ↓
필요하면 11_보완질문
        ↓
20_기초문서 작성 요청
        ↓
30_MVP 전체 구현 요청
        ↓
실행·테스트 확인
```

## 프로그램을 만든 이후

```text
ChangeRequest 복사
        ↓
문제 / 기대 결과 작성
        ↓
AI에게 수정 요청
        ↓
테스트
        ↓
완료
```

# 28. 이 템플릿에서 가장 중요한 원칙

마지막으로 이 템플릿을 사용할 때 다음 다섯 가지만 기억하면 된다.

**1. 요구사항에는 원하는 결과를 적는다.**  
구현 방법까지 사용자가 모두 설계하려 하지 않는다.

**2. 구현을 막는 질문만 한다.**  
사소한 것은 AI가 합리적으로 판단한다.

**3. 같은 사실을 여러 문서에 반복하지 않는다.**  
각 문서의 역할을 분리한다.

**4. 한 번의 요청으로 MVP 전체 구현과 검증을 목표로 한다.**  
AI 내부에서는 단계를 나누더라도 사용자가 매번 진행 승인을 할 필요는 없다.

**5. AI의 설명이 아니라 실제 실행과 테스트 결과를 기준으로 완료를 판단한다.**

이 원칙을 지키면 AI에게 매번 프로젝트 전체를 다시 설명하는 일을 줄이면서, 장기간 개발하더라도 비교적 일관된 방식으로 프로젝트를 유지할 수 있다.

---

## 참고: 현재 템플릿의 ChangeRequest 위치

현재 템플릿의 작업 절차에는 `docs/tasks/ChangeRequest.md`를 기준으로 설명하는 부분이 있지만, 배포된 템플릿에서는 `ChangeRequest.md`가 최상위 폴더에 있을 수 있다.

실제 프로젝트를 시작할 때 다음과 같이 정리해 두는 것을 권장한다.

```text
docs/
└── tasks/
    └── ChangeRequest.md
```

이 원본은 그대로 보존하고 실제 작업이 생길 때마다

```text
001_작업명.md
002_작업명.md
003_작업명.md
```

형태로 복사해서 사용하면 된다.
